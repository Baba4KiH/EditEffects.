EE. — ЗАПУСК И ПОДГОТОВКА К ПУБЛИКАЦИИ

1. ЛОКАЛЬНЫЙ ЗАПУСК В WINDOWS CMD

Скачайте и распакуйте проект. Используйте Node.js 24; ваша версия 24.22.1 подходит.
Откройте cmd и замените путь ниже реальным:

cd /d "C:\Users\user\Desktop\EditEffects.-publication"
copy .env.example .env
notepad .env

Команду copy выполняйте только один раз: не перезаписывайте уже заполненный .env.
В .env заполните TELEGRAM_BOT_TOKEN и TELEGRAM_CHAT_ID. Токен не присылайте в переписку.
Поставьте боту Start в настроенном чате. Остальные настройки для локального теста можно оставить.

Если нужен ваш Happ с HTTP-прокси на порту 10809, в ЭТОМ ЖЕ окне cmd:

set "HTTPS_PROXY=http://127.0.0.1:10809"
set "HTTP_PROXY=http://127.0.0.1:10809"
set "NO_PROXY=localhost,127.0.0.1,::1"
set "NODE_USE_ENV_PROXY=1"

Затем:

npm test
npm run telegram:check
npm start

Откройте http://localhost:3000. Отправьте форму с вымышленными именем и задачей,
например TEST PUBLICATION. Проверьте сообщение в Telegram и ответ сайта.
Не используйте реальные персональные данные: документы ещё не заполнены.
Остановка: Ctrl+C. После изменения .env перезапускайте сервер.
Для отдельного диагностического сообщения: npm run telegram:test (отправляет одно сообщение).

2. ЧТО УЖЕ ПОДГОТОВЛЕНО

Самостоятельный запуск без платформы статической публикации.
Локальный шрифт Manrope с лицензией; исправлены опечатки.
Форма отправляет на /api/brief; резервный контакт https://t.me/baba4kih.
Без скрипта отправка заблокирована, резервный POST не помещает данные в URL.
Ошибки посетителя не содержат инструкций по настройке сервера и токена.
Подробные фиксированные коды ошибок доступны оператору в журнале, без текста заявки.
Лимит 5 заявок в минуту на IP, honeypot, ограничение размера и проверка полей.
Защищённая обработка адреса клиента от явно доверенного прокси.
Страница 404 с правильным статусом, /healthz, кеширование статики.
Заголовки CSP, запрет встраивания сайта, Referrer-Policy, Permissions-Policy.
SEO-адреса, sitemap и robots.txt генерируются по SITE_URL.
Коды подтверждения поисковиков задаются в переменных окружения.
Тестовый режим не индексируется и показывает предупреждение.
Шаблоны Caddy (HTTPS и сжатие) и systemd (перезапуск службы).

3. ЧТО НУЖНО ОТ ВЛАДЕЛЬЦА ДО ПРИЁМА РЕАЛЬНЫХ ЗАЯВОК

Домен, выбранный хостинг и операционная система ещё неизвестны.
Нужен хостинг с постоянно работающим Node.js, а не только статическая папка.

Заполните privacy.html и consent.html под фактическую деятельность:
- кто является владельцем/оператором, страна работы, контакт для обращений;
- какие данные собираются и зачем, срок хранения и порядок удаления;
- кто имеет доступ, где находятся сервер и получатель заявок;
- как используется Telegram и какие передачи данных происходят;
- применимые условия согласия, его отзыва и учёта версии документа.
Не выдавайте текущие страницы за готовые документы. Проверьте требования с учётом
страны работы и аудитории; юрисдикция и сведения о владельце пока не предоставлены.
Галочка формы и дата в сообщении не заменяют необходимую процедуру учёта согласий.
Не добавляйте аналитику до решения вопроса о её настройках и отражения в документах.

4. НАСТРОЙКИ ПУБЛИЧНОГО СЕРВЕРА

Перенесите проект и отдельно создайте защищённый .env. Укажите:

NODE_ENV=production
SITE_URL=https://ВАШ-ДОМЕН
HOST=127.0.0.1
PORT=3000
TELEGRAM_BOT_TOKEN=ВАШ-ТОКЕН
TELEGRAM_CHAT_ID=ВАШ-ID
LEGAL_READY=true
ALLOW_INDEXING=false
TRUSTED_PROXY_IPS=127.0.0.1

LEGAL_READY=true допустим только ПОСЛЕ заполнения двух документов.
Сервер откажется запускаться в production с незаполненной конфигурацией
или исходными заглушками документов. Это проверка настройки, а не правовая экспертиза.
SITE_URL — полный HTTPS-адрес без пути. Сайт рассчитан на корень домена.
Начните с ALLOW_INDEXING=false. После всех проверок измените на true и перезапустите.

TRUSTED_PROXY_IPS оставляйте пустым при прямом локальном запуске.
Для приложенного Caddy на той же машине укажите 127.0.0.1.
Прокси ДОЛЖЕН перезаписывать X-Real-IP адресом клиента, а порт Node не должен
быть доступен извне. Не доверяйте произвольному X-Forwarded-For.
Если появится CDN или несколько прокси, эту схему надо адаптировать до запуска.
Несколько Node-процессов требуют общего хранилища лимитов; текущая схема — один процесс.

Проверьте доступ хостинга к api.telegram.org. Не переносите автоматически локальные
HTTPS_PROXY/HTTP_PROXY с адресом 127.0.0.1:10809: Happ работает на вашем компьютере.
При прямом доступе сервера к Telegram переменные прокси не нужны.

5. ПРИМЕР ДЛЯ LINUX VPS (АДАПТИРОВАТЬ ПОСЛЕ ВЫБОРА ОС)

Установите поддерживаемый Node.js 24 и Caddy средствами выбранной ОС.
Создайте отдельного системного пользователя ee и разместите проект в /opt/ee.
.env должен читаться только администратором и пользователем службы (например chmod 600).
Проверьте путь к Node командой: command -v node
Если он отличается от /usr/bin/node, исправьте ExecStart в deploy/ee.service.

Скопируйте deploy/ee.service в /etc/systemd/system/ee.service:

sudo systemctl daemon-reload
sudo systemctl enable --now ee
sudo systemctl status ee
journalctl -u ee -n 50 --no-pager

В deploy/Caddyfile.example замените example.com доменом, затем перенесите конфигурацию
в /etc/caddy/Caddyfile. DNS A/AAAA должны указывать на сервер; откройте входящие 80/443,
не открывайте 3000. Уберите неправильную AAAA-запись, если сервер не обслуживает IPv6.

sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy

Caddy обеспечивает HTTPS и gzip/zstd. Сертификат проверяется уже на реальном домене.
Если нужны www и адрес без www, выберите основной и настройте редирект второго на него.
На управляемом хостинге используйте его HTTPS, автозапуск и переменные окружения;
примеры systemd/Caddy там могут не понадобиться. HOST=0.0.0.0 нужен только если это
требует контейнер/платформа, с ограниченным доступом к внутреннему порту.

6. ПРОВЕРКИ ПЕРЕД ОТКРЫТИЕМ

- npm test проходит; npm run telegram:check подтверждает доступ к Telegram.
- Форма на HTTPS-домене доставляет вымышленную тестовую заявку ровно один раз.
- При потере сети остаётся понятная ошибка и доступен Telegram @baba4kih.
- Без JavaScript отправка заблокирована; имя/контакт/текст не появляются в URL.
- На телефоне проверить меню, обе темы, поля и клавиатуру, ссылки документов,
  вертикальную прокрутку над блюром и отсутствие кликов/свайпа карусели.
- Проверить Chrome/Firefox/Safari и ширины 320/390/768/1440, масштаб 200%, клавишу Tab.
- Проверить скорость и плавность блюра на реальном слабом телефоне (не проверено здесь).
- /несуществующая-страница возвращает 404; /.env и /server/index.mjs недоступны.
- /healthz возвращает 200. Настроить внешний мониторинг и уведомления оператора.
  Эта проверка подтверждает процесс, но не фактическую доставку сообщений.
- Проверить автоматический запуск после перезагрузки и восстановление службы.
- Хранить резервную копию проекта и настроек отдельно; .env не публиковать.
- Проверить CSP и консоль браузера; не отключать защиту целиком ради нового виджета.

7. ПОИСК И ПРЕВЬЮ

Укажите SITE_URL, затем проверьте исходный HTML: canonical, og:url, og:image,
Twitter Card и JSON-LD должны ссылаться на ваш домен. /sitemap.xml — на главную.
После готовности: ALLOW_INDEXING=true, перезапуск, проверка /robots.txt.
Добавьте новый домен в Google Search Console и Яндекс Вебмастер.
Выданные значения (только content, не полный тег) поместите в:
GOOGLE_SITE_VERIFICATION и YANDEX_VERIFICATION, затем перезапустите сервер.
Подтвердите права в кабинетах и передайте https://ВАШ-ДОМЕН/sitemap.xml.
Коды и домен не предоставлены — подтверждение и отправка карты ещё не выполнены.
Проверьте превью ссылки в Telegram; старое превью может кешироваться.
Старую тестовую публикацию выключите отдельно в её панели хостинга либо настройте
переезд на новый домен. Эта ветка не меняет настройки старой площадки.

8. ЧТО НЕ ПРОВЕРЕНО И НЕ НАСТРОЕНО АВТОМАТИЧЕСКИ

Реальные DNS/HTTPS, настройки неизвестного хостинга, автозапуск на нём,
доставка с будущего сервера, внешнее наблюдение и резервное копирование,
мобильные устройства и Safari, готовые документы и регистрация поисковиков.
Реальные сообщения и секреты в среде подготовки не использовались.
